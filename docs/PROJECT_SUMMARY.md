# Project Summary: C2 Program Status Reporting Pipeline

> **Update, October 2026.** The slide-deck finding in this document led to a second build: Workflow 3 and a `deck_service/` replace the template-based Workflow 2 with a deck that Claude builds each week, behind two human approvals. The new chapter ("Replacing the template") sits just before the recommendation, and the recommendation itself has been revised. The sections about Workflow 2 are kept as written because they explain why it was replaced.

## What this is

An n8n-orchestrated pipeline that turns a week's worth of Asana tasks, a risk register, a milestone reference sheet, and free-text engineering notes into a reviewed, human-readable weekly status report for a fictional defense program (Meridian Defense Systems, C2 Platform). Three LLM agents — an Analyst, an Executor, and a Slide-title compressor — run behind a small FastAPI service, each with its own instructions file, schema, and retry logic, so the orchestration layer (n8n) never talks to the model directly. The report is delivered by email; a Google Slides deck can optionally be attached to the same email, built from the same generated content.

The system is split into two independently-triggerable n8n workflows connected by one shared file on disk, plus the FastAPI agent service (`agent_service/`) that does the actual LLM calls and validates their output. Full wiring detail is in `README.md`; this document is the narrative — what was built, why it's shaped the way it is, what broke along the way and what that revealed, and an honest assessment of what does and doesn't hold up as a real weekly deliverable.

All of it runs locally, not against any cloud-hosted n8n instance: n8n itself in a Docker container on Windows, started via Docker Compose. The container needed access to the source data — `milestones.xlsx`, the task/risk exports, `program_notes.txt`, and the agent instruction files — which live on the Windows host, not inside the container, so a Windows folder is bind-mounted into the container's filesystem to bridge the two. The exact mount setup and its gotchas (permissions, which trigger node is safe to use on a Windows mount) are in the Setup section of `README.md`.

## Why two workflows, not one

Workflow 1 does the analysis: gather tasks/risks/milestones/notes, run each milestone through the Analyst and Executor, format a narrative report, and (optionally) email it. Workflow 2 takes the same generated content and turns one milestone into a populated slide, attached to a combined email.

These were built and are kept as two separate n8n workflows rather than one long canvas, connected only by a JSON file (`report_<date>.json`) that Workflow 1 writes and Workflow 2 reads. That decoupling was deliberate, not incidental: it means Workflow 2 can be tested, re-run, and debugged entirely on its own against a saved report, without re-spending LLM calls on Workflow 1 every time. Late in the build, a light coupling was added back — an `Execute Workflow` node at the end of Workflow 1 that automatically kicks off Workflow 2 once the sidecar file is written — but that's pure run-sequencing convenience. No data flows through that call; Workflow 2 still gets everything it needs by re-reading the same file it always has.

The alternative that was considered and rejected: merging the two workflows into one canvas, or using n8n's `Merge` node to combine live output from both into a single email. `Merge` only operates within one workflow's own execution graph — it has no way to reach into a second, separately-triggered workflow — so making that work would have meant collapsing the clean separation above just to solve an attachment problem. Instead, the two fields the combined email needed (`report`, `subject`) were added to the same sidecar JSON Workflow 2 was already reading, so the "merge" is really just two more keys on a file, not a cross-workflow call.

Delivery itself is left configurable rather than hardcoded to one shape. Workflow 1's own Gmail node (report text only) and Workflow 2's Gmail node (report text plus the deck attached) can both exist and both run — so a given week's output can be either two separate emails or a single combined one, just by toggling Workflow 1's Gmail node on or off. That's a deliberate switch, not an oversight left half-finished: whether a recipient wants a fast, deck-free heads-up followed by a fuller message, or just the one combined email, is a client preference, not something this project should decide on their behalf.

A Slack post to `#c2-program-status` was added as a third delivery path, alongside rather than instead of email — email and Slack solve different problems (an inbox item versus something the whole program channel sees and can react to or ask questions on in place), and there's no reason the pipeline should force a choice between them. The format was modeled directly on a manually-posted test message already sitting in that channel, so the automated version reads the way the team already expects a status update in Slack to read, rather than introducing a new format nobody asked for. Each week posts as its own message rather than a thread reply — the reasoning is the same as the two-emails-or-one decision above: a threaded history is tidier in the abstract, but it hides each week's actual content behind a reply count in the channel view, and this data is exactly the kind of thing people should see without an extra click.

Nothing public goes out unreviewed, though. Between drafting the Slack post and anything actually leaving the pipeline sits a human-in-the-loop approval gate: the drafted post is DM'd to a human approver in Slack, and only a click on Approve lets the run continue to the channel post and the slide-deck workflow. This was a deliberate late addition, not part of the original design — the first version of this pipeline auto-chained straight from report generation to both the Slack post and the slide-deck workflow, which is fine for a demo but is exactly the shape of automation a real defense-program status pipeline shouldn't have: an LLM-drafted weekly update reaching a program channel, or triggering a second workflow that spends further API calls and produces an attached deck, with no person ever having seen it first. Gating that behind a real approval step, rather than just documenting the gap or leaving Workflow 2 manually triggered, was the option chosen specifically because it's the version of this pipeline that would actually be defensible to run against a real program.

## The debugging trail, and what it says about the tooling

A lot of the actual time on this project went into the kind of failure that never shows up in a passing test suite — a workflow that "runs successfully" but is quietly wrong. Several of these are worth recording because they're not one-off mistakes, they're properties of how n8n's low-code model works:

**The native Asana node didn't expose enough of the data to be usable.** n8n's built-in Asana node returns a fixed set of fields per task, and that set didn't include the custom fields this pipeline actually depends on — "Related Milestone," "Likelihood," "Impact" — the fields that tie a task or risk to a milestone and let the Analyst reason about severity at all. The native node was dropped in favor of a plain HTTP Request node hitting Asana's API directly, which returns the full task object including custom fields. `map_asana_tasks.js` and `map_asana_risks.js` were then written to accept either shape (native-node output or raw HTTP response), so the rest of the pipeline doesn't care which route fed it — useful in case a future version of the native node closes this gap.

**Code node contents aren't linked to any file.** The `.js` files kept under `n8n/` in this repo (`format_report.js`, `build_slide_bullets.js`, `build_request.js`, `map_asana_tasks.js`, `map_asana_risks.js`) exist for readability and version history, but n8n Code nodes store their script as text pasted directly into the node itself. Editing one of these files changes nothing in the live workflow. This caused a real, hard-to-diagnose bug: two fields (`report`, `subject`) were added to the sidecar JSON and threaded through `build_slide_bullets.js` to support a combined email, the Gmail node was correctly configured to read them — and the email body still came back empty, because the actual `Read notes` node in Workflow 1 was still running its old script, so the sidecar it wrote never had those keys in the first place. Nothing about that failure looked like a sync problem from the Gmail node's side; the expressions were syntactically perfect and pointed at real, well-named fields that just didn't exist yet in the live data.

**A leading `=` typed by hand silently corrupts an otherwise-correct expression.** Once a field's expression mode is toggled on, n8n expects you to type only the `{{ ... }}` part — the `=` that precedes it in n8n's own documentation and in most written instructions (including this one, describing what to type) is implicit, added by the UI, not something to type yourself. Typing it anyway doesn't error; it just prepends a literal `=` character to whatever the expression evaluates to. This produced two separate real failures in the same session: a Drive file lookup that failed with `File not found: =1abc...` (a perfectly valid file ID with one stray character), and every Slides placeholder on a test slide rendering as `=ATO Approval Slipping Past Deadline` and `● =` for values that should have been clean. Both looked like data problems at first; both were entirely about where a single character was typed.

**`$('Node Name')` references are exact-string, and validated for connectivity but not for existence-under-a-different-name.** n8n's own graph validator correctly caught a case where a wired connection was accidentally broken ("No path back to referenced node"), but it can't catch a node simply being called the wrong name — an expression referenced `Copy a file` after the actual node had always been named `Copy file`, and the error surfaced as "the node doesn't exist," which reads like a wiring problem right up until you check the literal string.

**A resource-locator field's "From List" mode can only show what already exists, right now, in the connected account.** It has no visibility into a file that the current workflow run is about to create three nodes earlier. The fix is mechanical (switch to "By ID," reference the ID by expression) but the failure mode — "the file I need isn't in the list because it doesn't exist yet" — is easy to interpret as a permissions or sync issue instead of what it actually is.

**Pinned data replays silently, including across edits that should have changed the outcome.** After fixing the stray-`=` bug in every Replace Text field, a re-run still produced the old, broken output. The live preview under each field was clean; the actual exported deck wasn't. The cause was that `Copy file` had cached output pinned from an earlier run, so `Replace Text` was operating on the *same already-modified* Slides file from before — and since that file's placeholder tokens had already been consumed by the earlier (buggy) run, the corrected values had nothing left to replace. The run "succeeded" by every visible signal and still produced last week's mistake.

None of these are exotic. They're the ordinary failure modes of building on a visual, low-code orchestration layer where state (pinned data, cached previews, canvas-adjacent-but-unconnected nodes) is easy to lose track of, and where a tool like n8n intentionally hides most of the mechanics that would make these mistakes obvious in a plain codebase (a diff, a linter, an import error). Recognizing that pattern — "this looks like a data bug but it's actually a tooling-state bug" — became the single most repeated move of the whole build.

## Adding the approval gate: debugging across two systems instead of one

Wiring in the Slack human-in-the-loop step was a different flavor of debugging than the rest of the build, because the source of confusion was as often on Slack's side, or in the seam between Slack and n8n, as it was in the workflow canvas itself.

**A Slack bot app can only be installed into a workspace you actually administer.** The first attempt tried to install a custom app into what looked, from inside Slack's UI, like a normal workspace — it wasn't. One candidate turned out to be a personal account context, not a workspace at all; another turned out to be an externally-connected Slack Connect org (a channel shared into it by someone else's workspace), where a guest has no admin rights and can't install anything, custom apps included. Both looked identical to an ordinary workspace from the sidebar. The fix was to create a brand-new Slack workspace end to end — owned outright, with its own channel and its own bot app — rather than trying to make a borrowed or ambiguous one work.

**A DM from a bot is grouped under "Agents & apps" in Slack's sidebar, permanently, by design.** This produced a real moment of "the approval message isn't reaching me" that wasn't actually a bug — the DM was arriving exactly where configured, it just wasn't sitting under "Direct messages" the way a human-to-human DM would, and there's no setting that changes that.

**Missing OAuth scopes fail silently as empty dropdowns, not as errors.** With only `chat:write` and `chat:write.public` granted, n8n's Slack node Channel and User pickers simply had nothing in them — no error, no obvious signal pointing at scopes. Adding `channels:read` and `users:read` and reinstalling the app (which issues a new bot token) fixed it. A related, easier mistake: the approval recipient field defaulted to resolving to the bot's own account rather than a human's, which would have sent the approval DM nowhere a person could act on it.

**"Send and Wait for Response" isn't a distinct node in the palette — it's an Action on the ordinary Slack node**, reachable only after picking Resource: Message. Looking for a dedicated "approval" node type first cost real time before realizing the gate is just another action alongside "send a message" and "react," with its own Response Type dropdown (Approval, among others) once selected.

**A node can exist in old execution snapshots while being genuinely gone from the live workflow.** Opening a past execution's canvas shows a frozen picture of what ran *then*, node list included — it is not a live view of the current workflow. The `Call 'Slide Build'` node was accidentally deleted at some point during canvas edits, and because old executions still showed it (as they should, being historical), it wasn't obvious the live Editor canvas no longer had it. Every subsequent approved run would have silently stopped short of the slide deck, no error raised, until this was caught by deliberately comparing the Editor tab against an execution snapshot side by side.

**Re-triggering a workflow before resolving its pending approval spawns an independent execution, not a retry.** Each trigger of Workflow 1 that reaches `Request approval` opens its own Slack DM with its own Approve/Decline button tied to that one execution. Firing the workflow two or three times while debugging, without resolving each prior approval first, left several executions simultaneously "waiting," each with its own DM, and produced genuinely confusing mixed signals — a Slack post going out from one execution while the Executions list still showed another as waiting. The fix was procedural, not technical: use "Stop all" in the Executions list before every clean test, one run at a time.

**A successful send and a visible delivery are two different events, and the gap between them can be long.** Once the approval gate and both downstream branches were verified working — every node green, a real Gmail API response with a message ID and `SENT`/`INBOX` labels — the actual combined report-and-deck email still didn't show up in the inbox for over an hour. A plain Gmail-to-Gmail test message sent around the same time was similarly delayed by several minutes before arriving. Pulling the message directly from the Gmail account (rather than trusting the n8n execution log alone) confirmed the email had genuinely been delivered to the inbox at essentially the same moment the workflow finished — it just took the better part of an hour to become visible. Nothing in this pipeline caused that; it's Gmail-side latency, and worth remembering the next time "the email hasn't arrived yet" looks like a pipeline failure a few minutes after a run.

## Getting consistent output: repeated runs and prompt tuning

LLM output isn't deterministic, and a status report that reads differently in tone or conclusion every time it's regenerated isn't trustworthy enough to send to leadership unreviewed. `scripts/repeat_runs.py` exists for exactly this: running the same milestone scenario through the Analyst and Executor five times in a row and comparing the results against each other — not just checking that each run parses and validates against the schema, but checking whether five runs on the same input actually agree on the things that matter (the reported status, whether a risk gets flagged, sentence count, banned or loaded language).

That repeated-run process is what caught the most concrete instance of this: the Analyst's `milestone_status_flagged` yes/no field coming back inconsistently across otherwise-identical runs on the same input — sometimes correctly reflecting whether the milestone reference's stated status matched the evidence, sometimes not. That wasn't a schema bug; the schema already normalizes case and boolean variants for that field. It was the instructions themselves being ambiguous enough that the model's judgment on that one specific field wandered from run to run even though everything else held steady. Fixing it took several rounds of narrowing the Analyst's instructions — making explicit that the flag answers exactly one question (does the evidence support the milestone reference's stated status, and nothing broader than that) — re-running the five-pass comparison after each change, and only accepting a revision once the flag, not just the surrounding prose, came back stable across repeated runs on both known-answer cases (ATO, CDR). The current `agents/milestone_risk_analyst.md`, with its explicit worked rules around resource conflicts, what counts as "comfortable," and treating status and staleness as separate questions, is the result of that process rather than a first draft that happened to work.

## The core finding: template-based slide generation doesn't scale with the tooling used here

Separate from the debugging above, the slide-deck path surfaced a structural limitation worth calling out on its own, because it isn't something that better debugging would have fixed.

Google Slides' `replaceAllText` API (exposed through n8n's Replace Text operation) does exactly one thing: find a string in the presentation, replace it with another string. It cannot add a bullet, remove a bullet, or otherwise change the document's structure. That means any template built around it needs a fixed number of placeholder slots — this pipeline's template has five bullet placeholders per milestone slide — decided once, at template-design time.

The content going into those slots is not fixed. The Executor is instructed to write 1–3 sentences per milestone (occasionally more), which is exactly the right instruction for a narrative report but is fundamentally incompatible with a fixed number of slide bullets. Run the pipeline on a light week and two of five bullets are empty (a bare bullet glyph with nothing next to it). Run it on a week with a longer paragraph and the sixth-plus sentence has nowhere to go and is silently dropped — no error, no warning, just missing from the deck. There is no template design that fixes this, because the mismatch isn't in the template; it's between "a fixed number of slots" and "a variable amount of real content," and text substitution alone cannot resolve that.

The actual fix would mean not using `replaceAllText` at all for the bullet area: instead, deleting the placeholder paragraph and calling `insertText` plus `createParagraphBullets` in a loop, targeting the bullet list's shape by its object ID, to create exactly as many bullet paragraphs as there are sentences that week. That's a meaningfully different and larger piece of engineering than a `batchUpdate` of find-and-replace requests — object-level manipulation instead of global text substitution — and it was judged out of scope for what this project set out to demonstrate.

This wasn't a limitation specific to n8n's Google Slides node, either. Before settling on the Workflow 2 approach documented here, a parallel path was tried using Google's Gemini 3.8 Flash model to drive deck creation directly: same idea, template plus copy plus text-replace. It hit the identical wall — and the resulting pipeline was actually *more* complex than the one that shipped in Workflow 2, not less. Swapping which model or which orchestration tool is doing the driving doesn't make a fixed-template-and-replace approach materially easier; the ceiling is the technique, not the vendor.

A more interesting result came from a different angle entirely: giving Gemini's chat interface — not its API — a genuinely detailed prompt describing the week's data and asking for a coherent set of charts produced dynamic, well-composed, good-looking output, in a way none of the scripted, API-driven attempts came close to. That's a real and useful data point, but it points the same direction as the conclusion above rather than against it: what made that output good was a person sitting in a chat window, iterating and directing in real time, not something a script calling an API on a schedule can reproduce. The gap here isn't model capability — it's that current tooling makes the interactive, human-directed path meaningfully better than the autonomous, scripted one for this specific kind of layout and design judgment.

## Replacing the template: letting the model build the deck, and what it cost

The finding above ended on a distinction: scripted, template-driven slide generation hit a ceiling, while a person iterating with a model in a chat window did not. The follow-up build tested whether the model could be put in charge of constructing the deck without giving up the controls that make the rest of the pipeline defensible. The answer was mostly yes, with a caveat about money that is worth reading before copying the approach.

The design keeps the model's freedom narrow. A second FastAPI service, `deck_service/`, receives the week's approved sidecar and the milestone sheet and calls Claude with the code execution tool and the PowerPoint skill, using one saved instruction file. The deck is allowed to say only what a reviewer already approved: the service withholds the Analyst's own status and explanation notes, so nothing reaches a slide that a person has not seen in the report. An adapter joins the two inputs by exact milestone name and rejects a mismatch outright, rather than letting the model paper over a gap. The model's output is then treated as untrusted. The service renders the PDF itself and runs 21 deterministic checks in plain code: text overlap, shapes running off the slide, body text in the footer band, accuracy flags that do not match the input, ratings that appear nowhere in the source. Failures go back to the model, with page images, for up to two repair rounds. A deck always comes back if one was produced, marked `needs_review` if checks still fail, because the point is a draft a person can finish, not a pass/fail gate.

The approval structure mirrors Workflow 1. The draft is emailed to the reviewer and a Slack message says it is ready. Nothing goes to the distribution list until the reviewer approves, distribution is off by default and needs both a flag and an address list, and the file that is sent is the saved draft, not a regeneration. Declining hands the draft back to the reviewer to edit and send personally. The first reviewed deck needed only small corrections: a "Type" column that labelled items "Risk" or "Issue" when the approved text said neither, and a couple of titles that implied a slip the data did not show. Both were fixed with two sentences of instruction, and the decision was to stop there, since tuning layout details against fictional data would be tuning to noise.

The first live run cost $46.44. That was the most useful failure in the project. The cause was not the data, which was four milestones, but how a code-execution call works: each step the model takes in the sandbox re-sends everything accumulated so far, and the model kept going after the deck was saved, rendering it, inspecting it and checking its own work. The context grew from about 60,000 to over 500,000 tokens across 51 steps, and each step paid for all of it again, about 22 million input tokens in total. The deck had existed by roughly step 3. Four changes fixed it: a work budget in the instructions (write one compact script, run it once, print nothing large, stop), moving quality checking out of the model and into the service's own code, a hard cap of six model calls per request, and logging every call's token counts so the next surprise is visible immediately. A typical run is now one call of roughly 130,000 input tokens in about two minutes, or two calls and roughly 380,000 tokens in four minutes when a repair round is needed, which is on the order of $1 to $2 a deck. Along the way a 16,000-token output limit truncated the model's script before the deck was saved and the repair call then failed with a 400, which turned into a raised limit (20,000, since the SDK refuses more without streaming), an instruction to keep the script compact, and a clear error instead of a confusing one.

Delivery produced a second lesson. Slack's "Send and Wait" buttons are interactive, so Slack has to be able to post the click back to a public HTTPS address, and an n8n running on localhost cannot receive it. The buttons render and clicks do nothing, which looks exactly like a broken bot. Reading the documentation before suspecting the app would have saved an evening, as would checking which Slack workspace was open before concluding the bot had been removed. The resolution was a hybrid: Slack carries every notice and Gmail's Send and Wait carries the approval click as a link opened in the reviewer's own browser, which works locally. The Slack-button version is kept in `n8n/alternatives/` for an n8n with a public URL. Workflow 1's approval has the same limit and was not changed. Separately, Asana's trial ended partway through testing, and custom fields turned out to be a paid feature: Workflow 1's `Map tasks` node stopped with "No task has a Related Milestone value". That is recorded as a known limitation, since each user supplies their own Asana subscription the way they supply their own Anthropic key, and the Workflow 3 testing carried on from the saved sidecar instead.

What was tested is narrower than what was built. Workflow 3 ran end to end, through the build, the draft email and Slack message, the Gmail approval and a send to the reviewer's own address. The decline branch, Workflow 1 calling Workflow 3, the Slack-button variant, and data far larger than four milestones were not tested. Cost per call should grow about linearly with data, but that is an expectation, not a measurement.

## What this means as a recommendation

The text status report — Analyst, Executor, formatted narrative, delivered by email — works reliably end to end and needs no human intervention in the loop to produce a correct, well-formed weekly output. That part of the pipeline is genuinely production-shaped.

As originally built with the Slides template (Workflow 2), the slide deck is not, and shouldn't be sold as such. If a weekly slide deck is a real requirement from leadership, the honest options are: a person does final slide assembly each week, using the pipeline's generated titles, subtitles, and bullets as vetted raw material rather than final copy — or someone invests in the object-level Slides API integration described above, which is a genuinely different project, not an extension of this one. Treating "a human finishes the deck" as this pipeline's permanent, intentional design point — rather than a gap still to be closed — is the more accurate way to describe what was built here, and it's a more useful finding for a portfolio than a deck-automation feature that quietly breaks the first week the content doesn't fit.

The approval gate deserves the same honesty about its own edge. Right now a decline just ends the run — no record of why, nothing sent to anyone. That's a reasonable stopping point for a portfolio build, but it's worth being clear about *why* it stops there rather than treating it as finished: a decline on this pipeline almost never means "try again," because the report's content is entirely a function of the source data (Asana tasks and risks, the milestone reference, the engineering notes) — the Analyst and Executor aren't wrong so much as accurately reporting inputs a human judged weren't ready. The more complete version of this gate would capture the approver's decline reason (already collected by n8n's "Send and Wait for Response" node, currently just discarded) and route it to whoever owns the source documents, closing the loop back to the data rather than back to the pipeline. It wasn't built here because who owns that data, and how they'd want to hear about it, is a property of a specific real deployment, not something to guess at in a demo — a genuinely client-dependent decision, in the same spirit as the deck-automation call above.

The follow-up build changes the first half of that recommendation without overturning the second. A model-built deck handles variable content, which the template could not, and with controls around it (deterministic checks, a repair loop, two human approvals, distribution off by default) it is a reasonable "90% there" draft for roughly $1 to $2. It is still not a finished deck: the layout is sound but plain, some weeks need a repair round, and a person reviews every one. "A human finishes the deck" remains the intended design point. What changed is how much of the work the human is saved, and the cost of getting there was learned the expensive way: with agentic tool use, the number of steps and the size of the context matter more than the size of the data.
